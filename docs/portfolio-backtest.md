# 单账户离线组合回测 v1

本功能仅用于有限历史数据上的 BTC-USDT 现货、long-only、cash 回测。不会加载 `.env`、连接交易所、
签发 Proposal/授权或调用私有账户协调器。固定 60/40 示例是工程夹具，不是通过研究选出的组合权重，
所有报告均为 `trading_permission=false`。不得使用已经消费的样本外数据反复选权重或改参数。

## 三个职责

| 层次 | 实现与责任 |
|---|---|
| 策略意图 | 原注册表、Strategy/StatefulStrategy 和 FixedNotionalPositionSizer；策略只接收本实例不可变持仓快照 |
| 组合决策 | BudgetPositionSizer、组合风控和 PortfolioBacktestEngine；固定资金分区、扣费预算、账户敞口、确定性调度 |
| 成交与记账 | 一个 PortfolioBacktestBroker 的原 OHLC 撮合队列/成交量池；各策略复用 BacktestBroker 的成本算法，账户由这些分账与未分配现金汇总 |

原 TradingRepository、数据库结构、私有状态单写入口和受控 Demo 写权限不变。离线组合采用版本化 JSON
报告与检查点；不能把它的订单直接送入旧数据库或 Demo 路径，旧表尚未存储策略实例归属。

策略实例必须提供唯一稳定的 `instance_id`（字母开头，字母/数字/下划线/连字符，最多 64 位）。
同一策略不同参数必须使用不同实例 ID。新增的 `strategy_instance_id` 从信号贯穿 ProposedOrder、
OrderRequest、Fill、ClosedTrade、分账、事件和报告；默认空字符串保留旧单策略调用兼容。
组合路径以 run、实例、信号时间/序号派生确定性信号和客户端订单 ID，不使用随机 UUID 决定竞争顺序。

## 资金、归属和精度

- 固定分配之和不得超过账户初始资金，剩余现金明确记为 `unallocated_cash`，不借给策略。
  各策略保留自己的卖出回款和损益，策略之间不转移预算。首期只允许空仓初始化，未分配 BTC 为零。
- 现金余额包含冻结部分；可用现金 = 现金 - 未完成买单剩余数量 × 限价 × (1 + 手续费率)。
  同时检查所属策略和整个账户的可用现金。资金分区与账户现金都不能透支。
- 原始信号不改写参数。组合层将意图数量向下裁到扣费后可负担数量，再经过原最小订单、精度等风控。
  裁剪量为零或低于最小名义金额时明确拒绝。报告的 PositionSizeCalculated 保存原请求量及分配量。
- LIMIT 买单滑点后价格仍受原限价上限约束，故按限价加手续费预留已覆盖最坏成本，没有额外虚构滑点缓冲。
  手续费继续按成交名义金额以 USDT 扣取。每次成交扣掉真实成本，剩余数量继续预留；撤单/拒单不再占用。
- 卖单预留本策略的剩余 BTC，不能卖出其他实例或未分配持仓。同方向未完成订单仍受原重复订单风控约束。
- 成本继续采用原加权平均成本、买入手续费立即计入已实现损益、完整交易周期按实际成交总额结清的口径。
  账户没有独立的第二套平均成本更新器，其数量、成本、现金、损益均来自各策略账本之和。
- 数量向下量化到 quantity_step；价格、限价和保护退出沿用原撮合精度。低于最小数量/名义金额的零头留在
  所属策略，报告 `dust_quantity`，不抹账、不转给其他策略。现金及数量对账使用精确 Decimal；成本分摊造成的
  损益末位误差容许 1e-20 USDT，不用该容差掩盖实际现金或持仓差异。

重复的本地成交记账按 `(client_order_id, phase_timestamp)` 去重，相同完整负载不再记账，不同负载明确失败。
这是现有 OHLC 模型“一单每阶段时刻最多一次成交”的规则，不是可用于交易所增量成交的 ID 协议。
本地阶段执行异常会停止该 Runner，不允许导出成功报告/新检查点；需从上一份完整检查点显式恢复。

## 调度、行情与风控

K 线 timestamp 代表 UTC 开盘时间，仅接收已确认、严格连续、对齐周期的行情。重复、乱序、缺失或未确认
K 线在修改业务状态前拒绝。收盘生成的信号从下一根 K 线开始执行，不能用当前收盘信号回填当前成交。
V3 继续使用自己的已完成高周期指标和版本化状态。显式 warmup 不交易，目前只允许支持该契约的
StatefulStrategy；旧策略不具备显式 warmup，传入预热时明确失败，不能静默消费入场信号。

每个阶段：已有的保护退出优先；已有挂单按确定性 FIFO 撮合；上一收盘产生的普通退出先于入场；
同类新意图按 `priority` 从小到大、再按实例 ID 排序，同一实例内部保留信号顺序。
一个 Broker 负责 open/intrabar 两阶段，整根 K 线的 volume × participation 向下量化后只使用一次，
不会为每个策略或每个阶段重置。保护退出、普通退出和入场同样消耗这一份成交量。

每实例沿用全部原风控：单笔、方向、精度、最小订单、重复订单、行情新鲜度等；入场敞口不得超过其固定分配
及账户总敞口上限。账户级敞口包含其他策略持仓和所有待成交买单。每日损失、回撤、订单频率使用统一账户值。
达到损失/回撤限制时，下一已知开盘阶段撤销所有入场挂单。退出不受入场预算、最大单笔买额和入场敞口限制阻断，
仍需有本策略持仓、符合精度/最小订单/频率等安全规则。

敞口上限是入场准入限制，不是通过未来数据或自动清仓保证的净值硬上限：价格上涨可能使已持仓的市值被动超过
上限。报告明确显示 `exposure_breached_by_mark`，下一开盘重新检查、撤销会超限的入场挂单，后续买入继续拒绝。
保留原策略及保护退出处理持仓，不擅自引入新的强制清仓规则。若需要对市值上限自动减仓，须另行定义并冻结政策。

## 入口与报告

完整本地演示（输出目录必须不存在）：

```powershell
python -m scripts.demo_portfolio --output artifacts/portfolio_demo_new
```

脚本用 5 根合成 K 线、100 USDT、两个 buy_and_hold 实例，各请求 80 USDT，固定预算 60/40，
每根可成交量 0.5 BTC；展示预算裁剪、共享成交量竞争、带持仓/挂单的检查点和精确恢复对比。
它没有实际运行相同数量的分钟或天数，没有调用私有或公共网络。

读取本地配置、显式规则快照和 CSV：

```powershell
python -m scripts.run_portfolio_backtest --config configs/portfolio.offline.example.json --candles <开发或合成CSV> --instrument configs/snapshots/BTC-USDT.json --output artifacts/portfolio_run_new
python -m scripts.run_portfolio_backtest --config configs/portfolio.offline.example.json --candles <相同前缀加后续CSV> --instrument configs/snapshots/BTC-USDT.json --resume artifacts/portfolio_run_new/checkpoint.json --output artifacts/portfolio_resumed_new
```

CSV 必须提供已确认行情，缺失不会自动补数；配置不接受 mode、账户凭证或杠杆字段。
CLI 保存最终取消挂单前的完整检查点，然后结束有限回测并生成报告；恢复要求 CSV 的完整历史前缀与检查点一致。
Python API 支持 `advance(candle)`、`save_checkpoint(path)`、`restore(...)` 和归属校验的 `cancel_order(...)`。

`report.json` 包含账户/策略现金、可用预算、预留、持仓成本、占用资金、已实现/未实现损益、费用、权益、
逐单成交和账户资金曲线，以及配置、策略版本/参数、行情哈希。`allocated_capital` 是分配的原始资金；
`capital_in_use` 是成本加买单预留，`mark_exposure` 是持仓市值；`available_budget` 是未预留的分区现金，
不代表其他风控必然放行。基准仅使用同一账户总初始资金的现金持有，不给每个策略虚拟分配全部初始资金。

## 检查点与单策略兼容

格式 1 检查点保存完整行情/撤单命令日志、预热、配置、规则、源目录与依赖锁哈希、Python/Decimal 环境及重建状态摘要。
恢复用同一注册表和全部相同逐根逻辑重放，重建策略内部状态、订单反馈、持仓、成本、预留和成交去重，再比较完整状态。
配置、源码、锁、运行环境、规则、数据或状态不一致时明确拒绝，不重置策略继续跑。重建是 O(历史长度)，适合有限离线回测，
不是长期运行的增量恢复系统，也不自动安装依赖。普通旧策略通过重放恢复；V3 额外比对它自己的版本化 checkpoint。

文件先在同目录完整写入并 fsync，再通过排他 hard link 发布；已有报告/检查点绝不覆盖，发布失败清理临时文件。
只在本地 Windows 文件系统实际验证了此发布方式，没有验证跨平台、网络盘、磁盘断电或离线环境恢复。
内容哈希不是签名；能重写整包并重新计算哈希的人不受此约束。请保留原研究冻结与样本外消费记录，组合运行不解锁它们。

原 BacktestEngine/CLI 保持原单策略入口，空实例 ID 不改变原订单 ID、参数或撮合；旧 CSV 保持原字段。
组合入口单实例在预算/费用不构成约束时与原入口比较成交时刻、方向、数量、价格、费用、退出原因及经济结果。
若意图耗尽分区现金，组合入口会扣费裁剪，原单策略 Broker 可能直接拒单，这是显式的新预算分配行为。

## 后续受控 Demo 所需能力

本轮不接入 Demo。后续至少需要：在原数据库迁移机制中持久化实例归属、分区预留和交易所成交 ID；
将订单/成交/归属/预留与审计设计成可恢复的原子事务；通过 PrivateStateCoordinator 完成账户对账；
将分配结果绑定 Proposal 与一次性提交授权；处理 unknown 时冻结相关预留并沿原查询对账流程恢复，禁止盲目重发。
前序已经发现的私有事件“成交已存、库存更新中断后重放未补记”的跨阶段事务缺口仍需独立修复，不能把本轮离线分账
测试视作该问题已解决。真实连接、交易所费用币种、外部持仓、订单重启恢复和长时间运行仍需专门验证。
